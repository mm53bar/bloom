# 20260814 — One `CareEvent` table, and readings kept separate

## Context

Bloom needs to record watering, feeding, repotting, pest treatment and pruning. All five have
the same shape: a pot, a date, an optional product, an optional note. Five tables and five
models for that would be near-identical code five times over, and assembling "what has
happened to this pot" would mean merging five sorted lists.

Moisture readings look superficially similar — a pot, a timestamp, a value — but differ in
every way that matters operationally. They are generated by a machine rather than performed
by a person, they carry a numeric measurement rather than a description, they arrive in far
greater volume, and they are the input to a decision rather than the record of one.

## Decision

One `care_events` table with a `kind` enum (`watered`, `fertilized`, `repotted`, `treated`,
`pruned`). One `moisture_readings` table, separate.

`Pot#last_watered_on` and `#last_fertilized_on` read from the timeline rather than being
denormalized onto `pots`.

## Consequences

- Each pot has a single readable history, ordered once.
- Adding a sixth kind of care is an enum value, not a migration and a model.
- `last_watered_on` costs an association walk rather than a column read. At this scale
  (tens of pots, hundreds of events, eager-loaded via `Pot.with_care_data`) that is free. If
  it ever stops being free, denormalizing is a contained change behind those two methods.
- Queries wanting only one kind go through the generated scopes (`CareEvent.watered`).

## Alternatives considered

- **A table per care type.** Rejected: five copies of the same four columns, and a merge
  every time the timeline is displayed.
- **Folding moisture readings into `CareEvent` as a sixth kind.** Rejected: it would put a
  numeric measurement into a nullable column on a table about human actions, and mix a
  high-volume machine feed into a low-volume log.
- **Denormalising `last_watered_on` onto `pots` from the start.** Rejected as premature; the
  eager-loaded association already answers it without a query per pot.
